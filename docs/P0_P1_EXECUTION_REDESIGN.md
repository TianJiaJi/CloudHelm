# P0＋P1：操作级提权与结果说明

## 范围与证据

本轮只改常规命令的提权接口、按需认证、操作反馈和报告收尾；不重写 SSH/Pi，不扩展全套文件工具、任务权限模式、领域工作流或工作区。基线为 `34d8ce8`。未访问用户主机、真实模型、个人数据库或凭据。现有协议 fixture 是本地可重复回归，不是实际模型行为或 Linux PAM 验收；用户描述的失败尚未提供完整真实调用轨迹。

## P0 源码发现

- `remote-tools.ts` 暴露 `request_root_session` 与 `sessionId`；默认 sudo 返回 prepared 上下文，并非已认证 root。常规命令应直接表达权限需求，不要求模型管理内部会话。
- `operation-input-bridge.ts` 已按可信 askpass 事件请求密码，并限制重试、清理缓存；不能因接口重构丢掉这条链。
- `sudo-outcome.ts` 的 sudoers 拒绝来自输出推断，不能凭文本把业务状态改成“未启动”。自动后备必须有结构化证据；未取得证据时保留未知而不是重放。
- `su-session-program.ts` 已隔离认证 PTY 与业务执行，但常见 su 在一次错误密码后退出，现有单进程连接流程不能满足有界重新输入体验。
- `task-completion.ts` 当前已不强制提交报告才 answered；真正残留的耦合包括旧 `report` 恢复原因、基于 unverified 的界面继续入口，以及默认多维报告呈现。不能误称现有后端一律阻止完成。
- `work-journal.ts` 仍向模型提供 `submit_verification`，保留旧格式的证据/字段修复提示；常规工具集应避免模型为了报告填表。

## 提权契约

1. root 需求是操作请求，不是授权。普通账号优先 sudo；已确认 UID 0 不再套 sudo。
2. sudo 明确不可用且业务未启动，才可请求受控 su；root SSH 只允许用户显式选择。实际身份与命令必须在审核前确定。
3. 不提前根据 SSH 登录方式索密；只有绑定当前操作的可信认证通道请求输入。密码错误允许有界纠正；取消、拒绝、超时、接管不得变成换身份授权。
4. 缺少 sudo 时提示推荐配置，但不自动安装、不修改 sudoers。su 可以用于本次任务；安装/权限配置是新变更。
5. 业务已启动、部分失败或结果未知时先核验；不得为了后备或补输出重放。文件与原 SFTP 权限不因 su 自动提升。

## 结果与报告契约

- 统一反馈必须区分未启动、结束、未知、可能影响、认证及下一步指引；查询只读不证明进程已退出。
- 报告不是完成门槛。普通回答自然结束；变更给出简短事实摘要；详细操作、历史和检查按需查看。
- 常规工具不要求 submit_verification。保留已有历史解释和确定性检查，但不能将检查覆盖不足等同于业务失败，不能引导为报告重跑。
- 真实失败、未决结果、风险接受、审批及恢复机制原样保留。结束回答不等于业务成功，AI 结论不得覆盖后台事实。

## 回归与完成条件

- root 直执行、sudo 免密/需要密码/错误后重试/取消、结构化未启动后备、输出伪造拒绝、未知结果不重放、身份变更重新审核。
- su 免密、真实受控密码请求、有限次数重试、迟到输入/断线/取消/错误接收方拒绝；协议与实际 POSIX 链路证据分别记录。
- 正常答复不因缺报告失败，旧 report 原因不单独启动模型，失败和未知状态不会被摘要洗成成功。
- 针对性回归、全量检查、构建与可用 UI 冒烟；真实模型/服务器/其他平台未运行时明确标注。

## 实施状态

P0 源码核查完成。针对性基线回归：7 个文件、55 项通过（任务 bb7377e03，退出 0），覆盖 task-completion、sudo-context、privileged-runtime、verification-repair、verification-card、su-session-protocol 和 privilege。它证明现有测试基线可重复，不代表新设计已实现，也不是实际模型/远端验收。

P1 操作级提权已接通：`run_remote(privilege="root")` 在后台确认 UID，并在审核前规范化身份/命令。需要 sudo 后备判定时，固定执行组件先针对该次已审核的精确 argv 执行内部非交互 `sudo -n -l -- <目标程序及参数>` 查询；不启动业务程序，也不因列表认证策略索密。`listpw` 与实际命令的 `NOPASSWD` 不等价：查询因需密码等原因无法确认时，由控制端复核后执行原已审核 sudo 命令，只有该命令实际 askpass 才触发私密认证；查询不确定不能作为后备证据。只有查询明确策略拒绝或 sudo 缺失、无其他阻断时才可提出受控 su。它不是模型可用的探测，也不把目标替换成 root Shell；普通 sudo 输出仍不能证明未启动。

su 使用隔离认证 PTY；在已收到密码、未建立 root 业务通道、独立 su 返回明确认证失败时，最多三次请求；取消、未知交互、断线不自动重试。root SSH 保留为显式高级路径；按 SSH 服务端协商的认证方式或本地解析器确认的加密私钥需求提供私密输入，不按主机配置提前询问密码／口令。免密认证或无口令私钥不弹窗；密码及私钥口令最多三次尝试，取消、连接失效后不再提交回答。现有 sessionId 工具仍兼容，但不再是常规 root 操作前置步骤。

### 原生 HTTP fixture 的可复现端口问题

本机 `netsh int ipv4 show dynamicport tcp` 返回动态范围 1024–15000，其中包含 Fetch 禁用端口。受控 loopback 实验绑定 10080：原生 HTTP 请求返回 200，但 Node Fetch 在连接前报 `fetch failed`／`bad port`，连接数和请求数均为 0。这证明 `listen(0)` 成功并不代表所分配端口可用于 Fetch，能够造成已观察到的零请求症状。

`Tests/adapters/fetch-listener.ts` 在公开 fixture 地址前检查分配端口，仅释放并替换 Fetch 禁用端口；最多 16 次分配，真正的绑定错误直接失败。不尝试业务请求，不重跑测试，不修改生产重试、安全策略、断言或超时。新增确定性禁用端口、资源释放、限次、绑定失败及实际 SSE 回归。辅助逻辑 `be7106aa5` 的 28 项回归与类型检查通过；接入后增加实际 SSE 回归，并与本机 Node v24.22.1 的 82 个禁用端口对照，无遗漏。最终完整验收 **`bbf9f7f1e` 退出 0：171 文件／1707 项通过，7 文件／25 项环境跳过**（22 项 Windows 不适用的 POSIX/PTY、3 项外部 SSH opt-in）。TypeScript、ESLint、依赖边界（492 模块／1947 依赖）、800 行、测试布局、版本／更新日志、三入口构建及 Edge UI／Markdown／AI 面板冒烟全部通过；全量使用 `--maxWorkers=2 --bail=1`，未新增排除、失败重试或放宽超时。
