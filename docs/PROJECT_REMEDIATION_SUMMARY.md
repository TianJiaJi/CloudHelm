## 一、总体判断

CloudHelm 的问题不是单纯“审核太严格”，也不能直接归咎于“模型不够聪明”。目前同时存在：

- 本应正常继续的观察、局部失败、未派发操作，被升级为重放风险或主机写锁。
- 真正未决的远端风险，又可能因连接配置产生新 hostId 而不再阻断同一目标。
- 模型摘要、报告、UI 状态、连接恢复等职责，介入了不应由它们决定的授权或执行流程。
- 凭据、配置、会话、引用与日志在异常边界上缺少一致的提交、归属和回收规则。
- 工具能力主要依赖通用 Shell，环境事实、权限入口和文件编辑承诺尚不够一致。
- AI UI 仍缺普通正文流式投影；Markdown、代码阅读和输入交互不能仅靠仿照 Trae CN 的颜色与尺寸达标。诊断面板也挤占了正常对话。

**整改目标：减少无意义打断，同时加强真正的安全边界；保留已有安全基础，重做不一致的执行契约和跨模块约束，不做无差别全仓库重写。**

### 必须保留的安全基础

1. 所有 Agent 发起的远端变更仍经过统一 SafetyGate。
2. 授权继续绑定操作内容、目标、目录、身份、策略版本与终端/连接代次；派发前重新核验。
3. 密码和验证码继续通过独立认证通道；不得进入模型上下文、普通 Shell 输入或普通日志。
4. 后端仍是任务、审核、输入接收方、远端写权限的权威来源；Renderer 只投影状态和提交请求。
5. 停止模型、发送停止请求、远端进程实际退出是不同事实；未知结果不能直接重放。
6. 安全组件、授权绑定或关键持久化失败，不得自动放行。
7. 分层依赖、经过验证的固定依赖版本和版本化数据库迁移继续执行。

### 不应采用的“捷径”

- 全放行 Shell，或把 npm/make 等能运行项目脚本的入口直接当成低风险兜底。
- 只扩充只读命令名单，却不统一结果、恢复、防重放与调度的语义。
- 仅改提示词，要求模型“更小心”，替代后端约束。
- 删除所有未知锁，或给操作换 ID 来绕过旧未决风险。
- 用报告 verified、模型口头解释或普通新消息解除真实风险。
- 把所有错误都暂停整个会话，或者把全部风险判断交给用户逐条确认。

## 二、证据等级与优先级

### 证据等级

- **F：本地复现**。真实业务模块配合假传输、假模型输出、内存数据或故障注入；不是生产 E2E。
- **S：源码确认**。控制流/接口已确认，实际影响可能还需运行测量。
- **D：设计整改**。为解决已发现根因提出的结构性改进，不单独宣称为已复现 bug。
- **V：待实测**。需要实际安装包、真实隔离主机或模型任务验证。

同一条可能同时包含“已确认机制”和“未实测影响”，须分别解释。

### 优先级

- **P1：首批必须解决或建立的安全、执行正确性、恢复和工程验收基础。**
- **P2：核心能力、生命周期、性能与主要交互问题。**
- **P3：表达、信息层级和细节体验。**

这是实施排序，不是漏洞评级。下表共 **42 条整改/验收工作项**，包含合并缺陷、设计改进与验证工作，**不等于 42 个独立已确认漏洞**。

## 四、支撑总表的关键复现事实

### 第一轮：执行链与策略

测试环境：`mode: ask`、cwd `/srv/app`、没有额外保护路径；只分析字符串或使用假终端，不执行远端命令。

| 场景 | 本地观察 | 对应整改 |
| --- | --- | --- |
| lsblk、lscpu、ss -ltnp、ip addr show、df -h && free -m | 被判 ask / uncertain-command，但效果分类可为 effectFree=true | A05、A06；不意味着这些命令在所有环境都应免审 |
| 常见 head、tail、grep、du、ps、管道诊断 | 多种表达未获得一致的查询能力 | A05、C05 |
| npm install、make | 被判 allow / ordinary-command，尽管可能运行项目脚本 | A06 |
| grep 未匹配 exit 1；systemctl status exit 3 | 产生 possible-effects 未决链，后续写入虽获准仍被阻断 | B02、B07、B08 |
| ls 缺失路径 exit 2 | 被识别无变更，后续写入可正常派发 | 说明不能仅用“非零退出”判断风险 |
| ss -ltnp 获批成功后再次查询 | 第二次命中 replay-protected | B05 |
| 后台 http.server 仍在运行 | 阻断同主机普通写入 | C06；不代表应无条件解锁任意后台脚本 |
| 真实执行记录 succeeded，但目标未检查、报告 unverified | 镜像当前新轮次清理条件后，成功操作仍留在防重放集合 | B06；属于局部逻辑复现，不是完整真实会话 E2E |

`ask` 是审批打断，不等于硬拒绝。独立 AI 审核有 30 秒超时，也不等于每条命令都会调用或每次都花 30 秒。

### 第二轮：恢复、文件与界面

- 未批准的 proposed 恢复为 unknown 并需要核验：B01。
- 上传本地校验失败，远端调用为 0，结果仍解释为 unknown；运行时不锁、恢复后加锁：B03、B04。
- 假 SFTP 的非普通文件仍进入备份读取：C01；真实 FIFO 阻塞尚未实测。
- 原子替换仅传入部分 mode，没有恢复 uid/gid 的调用：C02；真实 Linux 最终属性尚未实测。
- 凭据服务不可用使整个 snapshot 失败，启动代码又在建窗口前读取 snapshot：F01；未进行真实 OS 凭据故障启动验收。
- 100 条各 10000 字符的其他会话历史，导致每次小思考更新的 JSON 快照约 1,010,694 bytes；3 次更新调用 3 次假凭据解密：F03。不是实际 IPC 字节数或 FPS 测量。
- 仅设置思考强度，connectHost 被调用一次：F02。
- 新输出无条件滚到底部：F04，为源码确认，未做本轮桌面交互复现。

### 第三轮：身份、授权来源、持久化与脱敏

- 只改超时时间，同地址/端口/用户名的新 hostId 不受旧锁阻断：A01。仍需新操作自身审核，不是跳过 SafetyGate。
- 地址 B/密钥 B 保存时密钥写入失败，runtimeProfile 返回地址 B/旧密钥 A：A02。未发送真实请求。
- 注入错误摘要后，摘要进入 explicit 意图，原禁止条件不在审核意图中：A03。不是实际模型误判率或真实破坏证据。
- ANSI 拆块、长敏感行溢出、多行 cookie 产生脱敏差异：A04。不是专用认证输入通道泄漏的证明。
- 删除持久任务时注入异常，当前内存任务消失、DB 仍存在、重新加载后出现：E01。没有删除真实用户文件。
- 删除发送会话后，原引用正文仍可从 SQLite 正常读取：E02。不是 SQLite 物理擦除问题，而是逻辑记录仍在。
- 自动引用捕获累积 1,048,576 个未换行字符仍未落该捕获的日志：E04。未制造实际 OOM。
- unknown 关闭后，尾片段在终端日志而不在 operation 日志：E03。操作快照 outputTail 仍可能保留，不是全部证据消失。

## 五、建议先统一的后端契约

以下是在已有类型上演进的职责划分，不要求照搬命名，也不意味着再创建一套重复状态系统。

| 契约 | 应负责什么 | 不应负责什么 |
| --- | --- | --- |
| 稳定目标身份＋配置修订 | 确定风险归属、连接目标和版本变化；保持代次/身份绑定 | 不能用新的配置 UUID 自动豁免同一目标旧风险 |
| 用户意图及来源 | 保存明确用户指令、引用来源、派生摘要和约束完整性 | 模型摘要、终端内容、普通报告不能自行获得用户授权身份 |
| 操作影响分析 | 描述可证明的读写/敏感访问/外传/资源边界和不确定性 | 不因为只读就替代所有访问控制，也不伪装为远端沙箱保证 |
| 操作身份与派发阶段 | 区分请求去重、用户新操作、重试；保存未派发/可能派发的可靠证据 | 不能仅靠命令相同或换 ID 决定是否安全；不能承诺网络边界天然 exactly-once |
| 执行结果 | 保存真实进程退出、原始退出码、影响证据和业务观察 | 模型总结不能写入进程事实；非零不能一概视为变更事故 |
| 阻断决策 | 给出原因、作用范围、解锁条件及允许的诊断/恢复动作 | 不能把所有局部错误变成全局暂停，也不能解除真正未知风险 |
| 持久化与恢复投影 | 提交事实后更新内存；确定重启后的同一语义 | 不能从报告标题、UI 状态或缺失字段猜测远端成功 |
| 展示与报告 | 解释事实、突出必要动作、提供证据与诊断详情 | 不控制锁释放、输入接收方、审核批准或远端派发 |

依赖方向继续保持：`application → core`、`adapters → core`、`desktop 装配 → application + adapters + contracts`、`renderer/preload → contracts`。共享事实不等于跨层反向导入，也不等于所有模块共享一个可随意修改的对象。

## 六、实施顺序与依赖

### 阶段 0：冻结验收基线与契约

- 收拢 H01、H02、H05，明确现有行为、目标行为和不允许破坏的安全基础。
- 建立 A05、B01、B02、B05 的核心语义，定义风险域、来源、派发与影响字段。
- 明确哪些旧记录可证明未派发，哪些必须保守保留；准备版本化迁移策略。

**出口：**跨模块测试能表达目标，不再由每个模块自行定义“失败/只读/未决”。此阶段不要求先把所有模块大重写。

### 阶段 1：先封住安全和持久化高风险边界

- A01：同一目标配置修订不能失去锁。
- A02：地址/密钥原子绑定。
- A03：摘要不能成为用户原始授权。
- A04：流式脱敏跨块一致。
- C01、C02：文件类型和元数据契约。
- F01：凭据故障不阻止修复界面。
- E01、E02：删除与引用生命周期。

其中 A02、A04、F01 等可在契约梳理期间先做局部修复；A01、A03 和恢复相关改动须与共享身份/来源设计协调。

**出口：**关键故障注入通过，不能新增授权、凭据或数据残留风险。

### 阶段 2：解决“每个命令都卡我”的执行链根因

- A05、A06：统一分析，修正查询与不透明项目脚本的分类排序。
- B01～B08：派发前失败、非零查询、恢复一致、防重放、新轮次、预检与阻断范围。
- E03：核验路径不漏操作日志尾部。
- H05：同时落地阶段计时，验证打断是否真正减少。

**出口：**普通诊断和显式新操作不再误锁；真正未知操作仍不能被重放或换 ID 绕过。

### 阶段 3：打通结构化能力、环境与后台控制

- C03～C07：安全文件编辑、统一权限、结构化诊断/服务、可证明范围的后台并发、终端释放/接管分离和精确单任务停止。
- D01～D03：观察与执行上下文一致、能力可用性和依赖边界。
- F02：设置和 SSH 生命周期解耦。

**出口：**三条端到端业务场景在隔离主机可稳定完成，不依赖模型临时拼装大量脆弱流程。

### UI 专线：与后端整改交叉推进，不再留到最后润色

- 首先建立真实内容与交互样例；Markdown、代码块、阅读层级、无活动诊断面板和消息操作可独立提前交付。
- 正文流式与增量性能同步设计，不能通过提高全量快照频率来假装补齐流式体验。
- 输入投递、停止范围、审批与未知结果入口依赖相应后端契约，不能只在前端换名称或猜状态。
- 具体工作包、依赖及验收见 [AI UI 专项方案](AI_UI_REMEDIATION_PLAN.md)。F06/G02 由原来的 P3 提升为 P2；这不改变安全边界的优先处理要求。

### 阶段 4：高频状态链与跨端呈现收口（非 UI 工作的起点）

- F03、E04：快照增量化、历史分页、有界输出捕获。
- F04～F06、G01～G02：滚动、作用范围、状态分层、结果/证据表达。
- 保留已实现的去重和中性结果展示，先定位实际黄色警告来源再动 UI。

**出口：**历史增长不拖累每次流更新；用户能读懂当前状态且不会误停止其他工作。

### 阶段 5：真实验证、影子比较和迁移收口

H03、H04 贯穿前面阶段，最后统一收口：隔离主机、真实模型任务、旧数据恢复、断线/停止/重启、性能与成本对比。仅比较新旧决策，不执行两遍远端操作。

**不要用全量换皮或堆工具替代执行语义整改；也不要因此无限推迟可独立交付的 Markdown、代码阅读与输入体验。**

## 七、统一回归验收矩阵

| 场景 | 必须满足的结果 |
| --- | --- |
| grep 未匹配、服务 inactive、查询路径不存在 | 保留原始退出和业务观察；无变更证据不产生错误变更锁；敏感读取策略仍有效 |
| 同轮重复 ss/状态查询 | 可重新观察，不误当变更重放；仍按当前目标和权限核验 |
| 用户明确要求再次执行已完成的同一变更 | 独立的新操作按当前风险重新审核；不受旧报告未 verified 的无关阻断 |
| 同一请求重复派发、丢确认后重发 | 不重复执行；不因换操作 ID 绕过未知结果 |
| 等待审批时退出/重启 | 可证明未派发的提案过期；不能要求核验根本没有执行的变更 |
| 上传源文件在审批后变化 | 远端调用为 0，提示重新准备；重启前后阻断含义一致 |
| 同目标仅修改连接超时/显示外的连接配置 | 原未决风险、互斥与恢复入口连续，不因新 UUID 消失 |
| 故意给出错误/丢约束的摘要 | 原始用户授权不变；派生文本不得冒充 explicit 授权来源 |
| 模型配置每一步写入故障 | 地址、密钥、版本保持完整旧值或完整新值，无混合配对 |
| OS 凭据服务不可用/解密失败 | 界面可启动并修复；相关模型/SSH 能力安全拒绝，不静默换账户 |
| 文件目标是 FIFO/设备等非普通对象 | 在读取备份前拒绝，不进入不受控读写；真实环境再验证挂起与取消 |
| 配置文件由服务用户/特殊组读取 | 编辑满足声明的元数据策略，或明确拒绝；不只校验内容 |
| 文件读取后被其他进程改动 | 根据版本/哈希拒绝过期写入，不静默覆盖 |
| 已知后台任务持续运行 | 仅在影响范围可证明时允许无关操作；不透明任务保持保守 |
| 点单任务停止或在 AI 终端按 Ctrl+C | 明示是否暂停模型，仅向指定目标请求停止，不误停其他后台任务；结果必须等待真实观察 |
| 多轮暂停/继续及显式人工接管 | 不无意义开启人工 Shell 或耗尽普通终端池；安全回收不抢人工、不关闭仍运行/未知通道，不丢操作证据 |
| ANSI、敏感字段、引号任意分块 | 不泄漏已支持秘密格式；溢出/EOF 后也不泄漏尾部 |
| 对话删除任一步失败/进程退出 | 可恢复到完整保留或明确待清理状态，无不可解释的内存/DB/会话文件分裂 |
| 引用发送、取消、丢弃草稿、删除会话 | 无孤儿正文；共享资料不误删；保留策略明确 |
| 操作 unknown 后关闭，最后一行无换行 | 所属 operation 日志保存已观察到的安全尾部，不串日志；不因此宣称远端已完成 |
| 持续无换行输出 | 内存有界，完整性状态明确，脱敏安全状态不丢失 |
| 历史会话数量/正文增长，小思考增量不变 | 高频更新载荷与重算范围不随全部历史线性增长 |
| 离线时修改思考强度等偏好 | 不连接 SSH，不弹远端认证，不因远端离线而无法修改 |
| 用户向上阅读持续输出的终端 | 不被新输出强制拉回底部，有明确新输出提示 |
| 登录 PATH 与执行 PATH 不同、工具存在但服务不可达 | 模型收到与实际执行相符的能力事实，不把 presence 当 ready |
| 停止模型、丢失停止回执、网络断开 | 不把 abort/请求成功当作进程退出，不自动重放未知操作 |

## 八、三条必须真实打通的业务链

### 1. 系统/日志诊断

环境观察 → 服务状态 → 有界日志读取 → 必要的重复查询 → 给出结论与证据。

重点：查询非零退出、组合查询、敏感日志保护、日志分页和准确的当前状态，不应被无关写锁或报告流程打断。

### 2. 配置修改 → 校验 → 服务重启

读取当前版本/元数据 → 生成差异 → 审核 → 条件写入 → 配置校验 → 必要的服务操作 → 独立读回/健康观察。

重点：并发改动、权限和元数据、失败后恢复、业务目标与进程成功分开；不将备份视为已经完成回滚。

### 3. 后台启动 → 查看输出 → 单任务停止

启动绑定明确的任务 → 获得真实进程/作业状态 → 增量查看输出 → 在允许范围做其他工作 → 单任务停止 → 核验退出。

重点：运行不等于未知；新配置不绕锁；局部控件不误停全部工作；断线/重启不伪造“已停止”。

## 九、仍需验证，不能直接当成已确认缺陷的事项

1. 用户实际安装包版本及黄色警告来源。当前源码已取消“必须交报告才能完成”，正常报告也不是默认黄色，不能把旧版本表现套到当前源码。
2. 实际 AI 审核频率、耗时、费用；30 秒是超时上限，不是已测平均耗时。
3. 真实模型任务完成率、指令遵循、工具选择质量。没有足够真实任务证据就不能直接断言模型能力差。
4. 真实桌面的首屏、流式渲染、IPC 体积、长历史 FPS 和内存；已有合成载荷证明路径放大，但不是实机性能数据。
5. 真实 Linux/SFTP 的 FIFO、权限、owner/group、ACL/xattr、断线中断和恢复表现。
6. 缺 Python、不同发行版、不同 PATH、非 systemd、Docker 权限等实际能力矩阵；当前发现是契约不一致，不能说所有主机都失败。
7. 细粒度资源锁的可靠性。仅靠模型声明“无关”不能缩小锁；强隔离需要远端最小权限或沙箱等真实执行边界。

已排除、不纳入整改缺陷的怀疑：

- “resume RPC 一定等待整轮模型执行，30 秒必超时”：当前 Worker 使用后台 resume 后立即返回。
- “日志视图因 report 回调每次变化而必然重置”：上层已有稳定回调，未证实该链。
