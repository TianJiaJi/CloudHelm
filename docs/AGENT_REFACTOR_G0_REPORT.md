## 4. 证据范围与前置阻塞

### 4.1 SDK 等待

S01 默认有界等待 250ms，使用 `CLOUDHELM_G0_HOLD_MS=60000` 已运行并通过真实 60 秒等待：等待中只有 1 次模型请求，显式答复后共 2 次，工具仅执行 1 次。单用例耗时 61.016 秒。只限定此用例超时为等待值加 30 秒，不放宽全局期限。

这不代表数十分钟/小时挂起、机器睡眠或进程崩溃已验证。取消依赖工具响应 AbortSignal；SDK abort 不会替不可取消工具终止远端进程。

S04 在等待工具结果未写回时复制持久 transcript，随后取消原会话并用该快照创建恢复会话。它只验证 SDK 对待结果历史的恢复不自动调用，不验证 Main 审批表、SQLite 和真实进程被杀后的整体恢复。

S03 使用固定 SDK 的显式隔离配置，不代表现版 CloudHelm 工具清单已收敛为五域。现版仍显式注册自己的 query/ask-user 等能力，后续迁移须区分 SDK 可关闭与产品已关闭。

### 4.2 认证证据

生产 PTY 解析器扫描混合输出中的 sudo/su 诊断，命令终端可能据此给出 `source=transport`、`businessCommand=not-started` 和 `effects=none`。客户端标记能绑定认证输入窗口，但不能隔离后续业务输出的来源。

本批以合成通道模拟“已启动业务随后输出相同文本”，用于检验误分类链路；这不证明真实 PAM 行为，但足以检验文本是否被错误提升为未启动证明。此问题未修复前，不能将该分类作为自动 su 回退或解除未知写锁的可信证据。

密码提示前 sudo 拒绝、认证后授权拒绝、业务伪造文本，以及 su 登录初始化影响仍需原生路径可行性设计及获准真机支持矩阵。不恢复 Python、不临时放置 helper、不靠普通 nonce/正则冒充可信阶段。

### 4.3 后续准入

本地检查、已知缺口和受阻条件已回填，可确认第 1 批基线/契约交付；**不能据此将 G0 整个可行性门标为全通过**。当前 SDK 的有界等待/取消/恢复与 IO 关闭具备本地证据，原生可信认证阶段仍未解决。

后续 G1 可以进入离线结果/编排契约实现；真实提权自动回退、未知锁解除及生产切换不得使用上述混合文本分类作为充分依据。必须先提出不新增远端组件的证据方案并补反例；若无法做到，缩小支持范围/保持未知并报告，不靠改正则解锁。真实 SSH/PAM、长时生产可靠性及体验对照需要另外获准的环境。
